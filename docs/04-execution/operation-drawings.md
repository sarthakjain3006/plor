# Executable Operation Drawings

## Idea

Setup, branching, and integration should begin with a simple drawing generated by the agent from the current node, repository, and conversation context. The user changes the drawing directly, runs it in an isolated Sandbox, inspects evidence on the same drawing, and iterates until the result is ready to approve.

## Core Concept

An `OperationDrawing` is a versioned, directed graph of typed operations presented as an approachable diagram. It replaces user-authored step lists and workflow configuration as the primary interaction.

The drawing contains:

- Operation nodes for agent tasks, Git actions, commands, checks, reviews, and final mutations.
- Typed directional edges for dependencies, requests, results, artifacts, approvals, context, and failure paths.
- Multiple handles and multiple edges between the same two nodes when relationships have different meanings.
- Human-authored labels, instructions, layout, and connections.
- Runtime status and evidence attached to the operation that produced it.

The drawing is an intent and review artifact. An immutable execution snapshot, rather than the mutable live canvas, is the input to a Sandbox run.

## Intent

Users should collaborate with an agent as they would at a whiteboard: see what it intends to do, reshape the approach, and ask it to prove the approach before anything becomes canonical. They should not need to write YAML, select a global workflow template, or understand orchestration infrastructure.

The visual language should remain small and legible. Formal structure exists underneath the canvas to make execution, authorization, history, and approval precise.

## Execution Concept

For a node setup or integration request:

1. The coding agent reads the relevant node context and proposes a drawing.
2. Humans and agents add, edit, remove, reconnect, and arrange operations.
3. The user chooses **Run in sandbox**.
4. The system freezes a drawing revision together with the expected repository heads.
5. The agent interprets and executes that revision in a separate Sandbox checkout.
6. Node status, output, logs, diffs, checks, and candidate artifacts stream back to the corresponding operations.
7. The user edits the live drawing or asks the agent to revise it, producing a new revision and run.
8. A final approval binds the accepted drawing revision to one exact candidate commit.
9. The platform performs the authorized setup or compare-and-swap integration mutation.

Execution does not pause source or destination nodes. Their agents and Sandboxes continue independently. A running Sandbox does not silently change checkout when a canonical Artifact advances.

## Technical Aspects

The initial canvas uses the MIT-licensed React Flow library. Custom nodes render operation details and status. Custom edges offset parallel and reciprocal relationships so dual edges remain individually selectable. A controlled graph model remains authoritative:

```ts
type OperationDrawing = {
  id: string;
  operationKind: "setup" | "integration";
  revision: number;
  contextVersion: string;
  nodes: OperationNode[];
  edges: OperationEdge[];
  runs: DrawingRunRef[];
};

type DrawingRun = {
  id: string;
  drawingRevision: number;
  drawingHash: string;
  baseHead?: string;
  sourceHead?: string;
  candidateHead?: string;
  status: "queued" | "running" | "failed" | "succeeded" | "approved";
  evidence: EvidenceRef[];
};
```

The NodeAgent owns drawing metadata and approval state. A drawing collaboration Durable Object owns ordered canvas mutations, presence, and short-lived cursors. Durable drawing snapshots and operation evidence live with the node record; large logs and exports live in object storage.

The coding agent accesses the canvas through structured tools such as `propose_operation_drawing`, `patch_operation_drawing`, `request_drawing_approval`, and `attach_execution_result`. Mutations carry an expected revision and never overwrite an unobserved human edit.

The local product prototype uses an in-browser execution simulator to exercise the complete drawing, revision, evidence, failure, iteration, and approval experience without credentials or container infrastructure. Production substitutes the Pi SDK adapter and Cloudflare Sandbox executor without changing the drawing model.

## Invariants

- Editing a live drawing never starts execution implicitly.
- Every run points to an immutable drawing revision.
- Every approval points to an exact drawing revision and candidate commit.
- A changed candidate invalidates approval.
- Agent canvas mutations are attributable, version-checked, and visible to collaborators.
- Source and destination nodes never pause merely because an integration operation exists.

## Failure Cases

- If a drawing contains a cycle or disconnected required operation, validation blocks execution and highlights the affected elements.
- If repository heads change, the candidate becomes stale and must be recomputed from a new immutable revision.
- If agent and human edits race, the stale mutation is rejected and the agent receives the current revision.
- If execution fails, completed evidence remains attached to the run while the editable drawing advances independently.
